# Beslut: auto-PR och refaktoreringsspärrar (2026-11-14)

**D31 – Workers skapar inga PR:er; `auto-pr.yml` gör det vid `[ready]`**
Workern behöver bara kunna pusha. När head-commiten på `claude/task-<id>` innehåller `[ready]` kör
`scripts/auto-pr.sh`:
- Titel: `<id>: <rubrik ur uppgiftsfilen>`. Beskrivning: journalfilen som lagts till på grenen, annars den
  senaste journalen för id:t.
- Etikett, i prioritetsordning: `blocked` (uppgiften har `status: blocked`), `conflict` (`[conflict]` i
  meddelandet), `needs-review` (storlek L), annars `automerge`.
- Idempotent: finns en öppen PR för grenen uppdateras titel, beskrivning och etiketter, och ingen ny skapas.

Workflowet använder `AUTOMERGE_TOKEN`, så att PR:en startar CI och `automerge.yml`. Med `GITHUB_TOKEN` skulle
inget av det hända. Logiken ligger i ett skript med `DRY_RUN=1`, så att den går att testa lokalt.

**D32 – Refaktoreringsuppgifter räknar blockerade beroenden som klara**
Fältet `kind: refactor` (005, 010, 015 och 020). En blockerad feature ska inte stoppa hela kön vid nästa
spärr. Funktionsuppgifter kräver fortfarande att beroendena är `done`. Ersätter nackdelen i D22.

**D33 – Konflikt- och blockeringsflödet går via commit-meddelande och status**
Konflikt: commit med `[ready] [conflict]` → PR med `conflict`. Blockering: `status: blocked` → PR med
`blocked`. Workern behöver alltså aldrig `gh` för att arbeta, bara för att frigöra döda lås.

**D34 – Ny etikett `needs-review`** för L-PR:er (tidigare: ingen etikett).
